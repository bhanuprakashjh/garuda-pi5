Chennai OAK camera handoff

Start with a tabletop object and your working CM3 tracker. Once the same tracker displays observations from OAK, use the camera for a separate handheld mapping session. You can try the first replay using the camera's factory values.

Unpack and set up once

Open the installation and first-session guide for the two-machine setup, video receiver command, recording transfer and Basalt download. Open that file through GitHub to read it formatted online.

Extract the ZIP into a new folder on the workstation. Copy that extracted folder to the Pi as ~/chennai-oak. Keep your modified source checkout and the delivered kit in separate directories. The receiving engineer owns the integration with the local tracker. Bench checks here use the camera and detector displays with the flight controller disconnected.

1. See the OAK in your existing tracker

  1. Save a reference. Point CM3 at a recognisable object such as a suitcase. Save the tracker's screenshot, current revision, camera selection and startup settings. Keep a way to select that CM3 profile again.
  2. Bring up the OAK camera owner on the Pi. Use the camera environment and the owner command under “Camera display, object detection and stereo” in the engineering guide. Use an existing owner if it runs this release with the required options. For an older service, follow the foreground check in the installation guide. The H.265 receiver IP is the laptop's address. The OAK owner serves the preview on port 8096.
  3. Check the image source. Open http://PI_HOST:8096/ in a browser, substituting the Pi hostname. Move the suitcase into frame. In the existing GARUDA demo, open Open bench camera demo from the launcher. Your custom GUI may use a different address or route.
  4. Your integration point is the image input. The supplied OAK capture adapter presents the single colour camera to the host detector. Keep the existing model and tracker for this comparison. The two monochrome cameras feed the Pi stereo computation. Their depth corresponds to the OAK colour view. Keep CM3 results under the CM3 profile.
  5. Move the suitcase across the view with the camera stationary. Look for fresh detections, a box moving with the object, and the tracker's actual behaviour when the object leaves and re-enters. Cover the OAK colour lens briefly to confirm which camera the tracker is using. Repeat the CM3 check after switching back. Record any differences for your own merge.
  6. Check distance and video separately. Use a rigid board and measured tape readings at near, middle and far positions. In the existing calibration GUI choose Open guided camera calibration. The H.265 receiver should show a moving picture with the target moving in the same direction. The H.265 picture comes from the camera encoder before any detector overlay.

Keep: a short bench clip or screenshots, camera profile and revision, measured depth readings and receiver result. Check bench camera signals in the launcher saves a read-only receipt from the standard camera and detector endpoints. A custom Chennai API may lack those fields; the receipt shows which ones need a manual check. A changing relay counter shows frames entering the Pi’s RTP payloader. Confirm delivery by watching the moving picture on the receiving laptop.

2. Record a handheld walk on the Pi

Point the OAK at a textured, stationary room. Stand behind the lenses. Hold still for a few seconds, walk slowly past some furniture, return to the starting mark in the same orientation and pause again. This is a separate camera session. The helper temporarily pauses the active camera services and requests their restart when it exits.

cd ~/chennai-oak
bash record-handheld walk 90

The default OAK interpreter is ~/.venvs/oak-bringup-3.12.1/bin/python. Override it with OAK_PYTHON if yours differs. The default service names are garuda-oak-preview garuda-mono. If your camera owners use other systemd names, set OAK_CAMERA_SERVICES to those names first. The helper uses sudo for the temporary systemd job. Let it reach its requested duration, then verify the bench preview is back.

Copy the whole new folder printed by the helper from ~/oak-recordings/ to the workstation using your usual file transfer. A valid take contains left/, right/, frames.jsonl, imu.jsonl, calibration.json and session.json. The last two describe the capture and its factory values. Keep all later fitted files in the result folders.

3. See the first path

Choose Try a handheld replay. Select the Basalt release folder, the copied walk recording, and an output location. A plot opens when processing finishes. Use the PyPI or OS Python environment that contains OpenCV and NumPy to launch the workstation application. A ring marks the start and a dot marks the finish. Look for a plausible movement and return. Save run/path.png, run/trajectory.txt and run/replay.json. The output folder also contains the exact configuration and logs. A plausible shape justifies proceeding to measurement.

4. Calibrate this physical camera

  1. Write down the unit's serial/asset label, capture mode and board ID. Use the same camera and resolution for both fits and validation. Create a workstation results folder labelled with that serial. The Basalt calibration JSON does not identify the camera for you.
  2. Print the A4 VIO AprilGrid at actual size, attach it to rigid flat backing and keep it still. Measure the black tag edge and adjacent white gap in millimetres, in both directions. Check the 100 mm scale bar. Reprint if horizontal and vertical scales differ. This sheet uses the Kalibr 6 × 6, 36h11 layout and a two-cell black border. The earlier checkerboards belong to the depth check. Kalibr target reference
  3. On the Pi, run bash record-handheld camera-grid 90. Show the fixed board to both lenses, centred and toward the image edges, close and farther away, with several angles. Pause at each pose. Inspect the detected corners in both images and move closer if the tags are too small to detect. For the second take run bash record-handheld imu-grid 90. Keep the board visible while moving and rotating the camera around all three axes. Avoid blur. Copy both complete folders to the workstation.
  4. Choose Fit stereo cameras. Pick the camera-grid take and enter the physical measurements. The launcher prepares raw paired images and opens Basalt. Follow the on-screen sequence, inspect detected corners and residuals, press save_calib and close the Basalt window. Keep the result folder.
  5. Choose Fit camera and IMU. Select the moving IMU-grid take and the previous stereo result folder. Choose measured IMU noise values if you have them, or explicitly select the exploratory defaults. Fit the relative pose and time offset in the Basalt window, inspect, save and close. The result folder contains a new calibration.json, the board measurements, the noise choice and the take references. The stereo result stays available.

5. Test the calibration on a different walk

Mark A, midpoint M and endpoint B on a straight line. Measure A–M and M–B. Record two independent walks in order A → M → B → M → A, setting the camera down in the same orientation for several seconds at each of the five stops. Use bash record-handheld validation 90 for each take. Record the rest times as a cross-check.

Choose Replay a measured calibration and build a map, select a held-out walk and the camera–IMU result for that unit. Then choose Score a measured walk, select the output folder containing run/ and dataset/, and enter the two tape measurements. Check the identified rests against your notes. Report failed takes too. The map replay writes keyframe data and the mapper log. The path plot shows the odometry estimate.

If a step stalls

  • OAK preview works but the tracker still shows CM3. Check the selected capture backend and image source in Chennai's modified application.
  • Camera busy. Check the camera owner/service names. The recorder and live preview each need exclusive access to the OAK.
  • Missing Basalt executable or library. Select the unpacked Linux release root, then inspect the result folder's operator.log for the missing library.
  • No corners or the solver fails. Check the correct board, print scale, lighting, coverage in both images and blur. Use a fresh capture and result directory.
  • Tape scorer cannot match rests. Check the route and gyro rest intervals. Smooth straight translation can also look quiet to a gyro. Repeat with clearly marked stops if the correspondence is uncertain.

The AprilGrid layout follows the ETH Zürich Kalibr target generator and the AprilTags 36h11 code family. For individual commands, inputs and output formats see the mapping engineering guide.
